# 分類基準

## 構造から推定する難度

公式SDKの難度指標を、その版のまま使います。変更の分散、変更量、課題文と変更の対応、テストの構造から得た指標です。正解パッチを含む開発用データから計算するため、提出エージェントの入力や隠れた本番問題の推定には使いません。

低い値は変更が小さく局所的である可能性を示します。モデルが解ける確率ではありません。少ない行の変更でも、互換性・境界条件・固定文言・複数の呼び出し経路が障害になります。課題IDは元のPR番号であり、難度順とは扱いません。

## 課題文の確認

手動の確認は以下の4項目を同じ粒度で記録します。

| 項目 | 確認する内容 |
|---|---|
| 対象箇所 | 修正する機能や場所が明記されているか |
| 期待動作 | 変更後に満たすべき動作が明記されているか |
| 再現方法 | 入力・操作・失敗例から問題を再現できるか |
| 修正方針 | 具体的な変更方針が示されているか |

値は`explicit`（明記）、`absent`（確認したが記載なし）、`unknown`（未確認）です。確認済みの問題には短い根拠も必須とします。未登録の問題は全項目を未確認として扱います。課題文の文字数、テンプレートの長さ、SDKのEasy分類だけで明確さを判断しません。

構造指標と課題文の確認は、次に調べる対象を絞る材料です。既存比較6問の平均成績を、全129問や正式評価の予測値として使いません。

## 実際の成否

成否は候補・実行ID・問題IDに対応づけます。公式判定の解決／未解決と、参照パッチの検証、個別テストの通過数を混同しません。未評価の問題を未解決にせず、構造上の難度を結果に合わせて書き換えません。

過去結果の結合は任意です。指定した記録は完全性を確認します。入力データのハッシュ、実行の完了、公式結果と集計の一致を検証します。詳しい失敗原因は既存の`analyze`を使って調べます。

## GPU費用

起動時間、生成時間、採点時間、保存時間、Notebook全体の時間、GPUのquota時間は別項目です。既存記録で分離できない項目は未確認とします。`evaluation_seconds`は生成・採点を含む時間であり、生成だけの時間として扱いません。

問題数別の見積もりでは、各実行の固定費を残し、生成・採点時間を問題数に比例させます。quotaは同じ実行の実測消費から換算します。2実行の最小・最大は観測に基づく幅であり、統計的な保証や将来の上限ではありません。

次回の問題数は、実行時の残枠、予備枠、Notebook期限、問題の構成から判断します。起動の固定費が大きいため少数実行にも費用がかかりますが、6問を最適数と判断しません。

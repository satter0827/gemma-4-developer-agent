# Easy課題の改善方針

公開課題129問のうち、公式SDK 0.2.11の構造指標でEasyに分類される課題は48問です。FastAPIが19問、Richが20問、Requestsが9問です。この指標は参照修正の規模や構造から求めた推定であり、実際の解決率や正式採点の難度を保証しません。問題IDの大小は難度の根拠にしません。

調整用は36問（FastAPI 14、Rich 15、Requests 7）、確認用は12問（FastAPI 5、Rich 5、Requests 2）です。既に調査・実行した課題を調整側に残し、未使用の候補からリポジトリごとに `SHA-256("0:" + 問題ID)` の昇順で確認用を選び、一覧を固定しました。選択時にモデルの成否は使っていません。確認用の内容や成否を改善の判断に使った場合、以後は独立した確認用と呼べません。使用履歴を残し、新しい実験の役割を明記します。

初回の対象は、FastAPIの14873・14479、Requestsの7328・7433、Richの3130・3278です。リポジトリを分散し、既存の比較6問とは異なる挙動を確かめます。これは最適な6問という主張ではありません。後続の調整では未使用の課題を優先し、実行前にIDと順序を固定します。環境検証に失敗した課題を実行時に補欠と交換しません。

## 既存結果が示す失敗

同じ6問を31Bモデル、生成5分・30ツール呼出し・50ターンの上限で評価したところ、基準は2問、手順を明記した指示は3問を解決しました。Requestsの2問は両者が成功し、FastAPI 14786は後者だけ成功しました。これは開発用6問の観測であり、Easy全体や非公開課題の解決率ではありません。

| 課題 | 観測した結果 | 改善の狙い | 残る不確実性 |
|---|---|---|---|
| Rich 3052 | 生成パッチの公式検証は失敗。個別テストは6成功・1失敗。大小文字の許容判定を直しても、公開APIの戻り値が正規化されず `FoO` が残った | 内部関数の確認に加え、公開APIの戻り値を検証する | 独立した検証担当によって実際に成功へ変わるか |
| FastAPI 14360 | 約308秒で時間切れ。最終変更は再現用スクリプトだけだった。問い合わせモデルの問題を異なる依存注入方法で試し、例外を捕捉して表示していた | 課題文の入口で再現し、失敗時には非ゼロ終了する検証を使う。実装の差分を確認する | ツール引数の不備が生成側と変換側のどちらで生じたか |
| Rich 3180 | 約304秒で時間切れ。最終変更は再現用スクリプトだけだった。未修正で110成功・4失敗 | 検証担当へ残時間を渡し、実装の変更と再試験を必須にする | 複数の境界条件を共有予算内で修正できるか |

FastAPI 14360の古い基準実行にはコンテキスト長超過もありました。後の手順付き実行は履歴圧縮後も時間切れとなっており、同じ原因として数えません。生成時間・ツール予算・ターン数・コンテキスト長の上限による停止は、固定条件の下での未解決です。採点処理のタイムアウトやサンドボックスの実行障害とは区別します。公式結果のerror欄に値があるという理由だけで、比較全体を無効にはしません。

保存されたツール引数には必須引数の欠落が見られますが、生のモデル応答がないため、モデルとパーサーの責任を断定しません。

`edit_file` または `write_file` の呼出しは、実装変更の成功を意味しません。再現用ファイルの編集、実装らしいパスへの試行、不明な対象、引数エラーを分けます。公式結果、個別テストの件数、トレース上の行動も別々の証拠です。確認できない値は未確認のまま扱います。

## 比較する構造

最初の実モデル比較は、既存workflowへ検証Skillだけを追加する構成です。モデル、LoRA、指示、生成・採点条件を固定します。担当を増やさず、テスト0件と実装差分なしを識別する効果を確認します。

修正担当の後に検証担当を実行する `SequentialAgent` は、CPUの契約検証まで完了しています。実モデルの有効性は未評価です。修正担当は調査・実装・初期テストを行い、原因、変更箇所、検証結果、未確認事項だけを引き継ぎます。検証担当は原課題と実際の差分を読み直し、公開APIと境界条件を検証し、必要なら修正・再試験してから提出ツールを呼びます。

修正担当には提出ツールや他エージェントへの転送を与えません。検証担当も転送できません。検証担当には過去の調査履歴を渡さず、原課題と短い引き継ぎを明示します。31Bモデルとサンプリング条件を固定し、5分・30呼出し・50ターンを2担当で共有します。補助担当とLoRAの割当にも差があるため、主指示だけの効果とはみなさず、担当構成全体の比較として扱います。担当ごとの時間配分は公式の宣言形式では強制できません。検証段階へ到達したかも評価します。

構造の比較は、担当の分離、検証手順のSkill化、主指示の自動最適化を一つずつ扱います。三つを同時に変更すると、どの変更が効いたか分からなくなるためです。追加学習は対象に含めません。

検証Skillでは、モデルが選んだ既存テストの終了コードと収集件数、実装差分をまとめて確認します。テスト0件や再現用ファイルだけの変更を成功とみなさないための手段です。期待動作の理解とテスト選択はモデルに残るため、Skillが成功しても課題解決の保証にはなりません。

主指示の自動最適化では、GEPAによる候補生成を最大1回、評価を最大8件に制限します。探索3問と選択3問はいずれも調整用です。反省に渡すのは行動上の観測に限定し、参照修正や課題固有の解答を渡しません。この規模では最適な指示が見つかる保証はなく、候補の採用には別の固定比較が必要です。

確認用12問は、これらの指示調整や探索へ渡しません。次の調整課題は成績で選ばず、未使用を優先してFastAPI、Rich、Requestsを巡回します。同じリポジトリではseed 0と問題IDのハッシュ順を使います。最初の巡回はFastAPI 14297、Rich 3944、Requests 6592、FastAPI 14463、Rich 3006、Requests 6589です。問題IDの大小と難度の関係を仮定しません。

## GPUの使い方

既存2実行のモデル起動は約865秒と1161秒、全体は約2505秒と2573秒でした。quotaの実測は約1.396時間と1.434時間、合計約2.830時間です。起動時間の幅が大きいため、問題数に比例した費用とみなしません。

新しい比較はモデル起動を1回にまとめ、課題ごとに2候補をAB、BAの順で交互に実行します。モデルとLoRA以外の会話、作業領域、評価器、保存先は共有しません。prefix cacheは両候補で無効にします。

二候補を比較するセッション上限は90分、後始末用は5分、各評価の追加時間見積もりは1分です。生成5分と採点5分を含む2候補と後始末が収まる残時間がなければ、新しい組を開始しません。起動遅延で全課題が終わらない場合も、延長や自動再試行はしません。片方しか終わらなかった課題は比較から外し、未完了として残します。

quotaは壁時計時間と区別します。開発予算は合計7時間、残す予備は1時間、係数は2です。90分の比較上限はquota最大3時間で、既存消費2.830299時間を含めても予備を確保できます。追加GPU実行はSkill比較1回に限り、途中停止や基盤エラーでも追加実行しません。残枠が不明な場合も実行準備を止めます。

評価では、両方成功、基準だけ成功、候補だけ成功、両方未解決を同じ課題内で比較します。実行エラー、片方未完了、未実行を別に記載し、異なる課題群の率を足し合わせません。CPU検証や合成応答の成功を精度改善と呼びません。

採用には全6問・両候補の公式結果、候補だけ成功した課題が1問以上、基準だけ成功した課題が0問、比較を無効にする基盤エラーや証拠の不一致がないことを要求します。同点、部分比較、行動だけの改善は保留します。この基準を満たしても、6問の改善は競技全体の精度保証にはなりません。

## 課題環境の成立条件

参照修正が失敗する場合、モデルの課題成績として数えません。RequestsのテストはローカルHTTPサーバーの待受が必要です。端末から継承したNO_COLORはRichの色比較を変えるため、表示用環境変数は課題テストから除外します。

Rich 3130の固定スナップショットはPygments 2.15.1を使用しており、新しい版ではテーマの色と空白の色が異なります。この課題に限り、スナップショットのlockに記載された2.15.1のWheelとハッシュを使います。テストの期待値や対象範囲は変更しません。共通の依存lockと過去の比較環境は保持し、課題専用の依存指定をCPUとKaggleの開発用サンドボックスへ同じように適用します。正式採点環境で同じ補正が行われるとは限りません。

最適化の時間上限は、候補比較とは別に決めます。現在の上限条件では、モデル起動、最大8評価、指示生成、CPU準備、後始末を含め約125分が必要です。90分をそのまま使うと、宣言した最大回数を完了できないため、GPU時間とquotaは明示設定とします。合成応答とCPUコンパイルの成功は、実モデルの精度改善を示しません。

# 設計

## 責務の分離

| 担当 | モジュール | 役割 |
|---|---|---|
| 設定 | `config.py`、`diagnostic_config.py` | 実行条件と診断入力を型付きで検証 |
| 診断 | `diagnostics.py` | CPU環境の準備、作業コピー、パッチ適用、テストと記録 |
| 公式基盤との接続 | `official.py` | コンパイル、参照検証、モデル登録、評価APIへの接続 |
| Kaggle実行 | `runtime.py`、`environment.py`、`kaggle_bundle.py`、`diagnostic_kaggle.py` | 依存導入、実行順序、ソースの固定とCPU診断 |
| 結果処理 | `results.py`、`diagnostic_results.py`、`artifacts.py`、`packaging.py` | 保存結果・JUnitの照合、ハッシュ、提出ZIPの検証 |
| 操作 | `cli.py` | 引数、処理への振り分け、結果表示 |
| 品質確認 | `scripts/check_coverage.py` | 行・分岐カバレッジの最低率を個別に判定 |

ローカル診断は推論ライブラリを読み込みません。Kaggleの依存導入は専用モジュールに置き、明示的なCUDA確認とモデル起動はGPU評価の段階に限定します。CPUの提出物コンパイルで必要なモデル・LoRA登録確認は維持します。

提出エージェントは公式の宣言形式で管理します。ルートのYAMLからプロンプト、生成設定、補助エージェント、配布LoRAを参照します。エージェントのループ、ツール、検証、採点は公式基盤が担当します。

開発基盤は、設定を公式APIへ渡し、実行したソースと提出物を記録します。CLIは準備・診断・結果表示を担当する処理へ入力を渡します。Kaggleの状態確認、アップロード、結果取得には公式CLIを使用します。

Pythonの識別子・コメント・docstring・ログと、エージェント向けの指示は英語です。CLIの利用者向け説明と開発文書は日本語です。新しいSkillや学習処理は初期構成に含めません。

## 設定と実行

評価の上限は提出物の`evaluation`設定だけを読み込みます。4項目を必須とし、欠落や不正な値を初期値で補いません。これは公式CLIの時間初期値とサンプルの設定が異なるためです。

比較用の評価設定は`prepare-kaggle --eval-config PATH`で指定します。省略時は`agent/eval_config.yaml`を使用します。選択した設定だけをZIP内の同じ配置へ格納し、選択元のパスとハッシュ、適用値を記録します。元の設定は変更せず、未使用の比較設定も送信しません。

Kaggle設定は指定モデル、公式Wheelhouse、実行イメージ、GPU設定、対象課題を持ちます。初期構成はL4を4基使用します。利用可能なGPUが異なる場合は、別の条件へ自動変更せず終了します。

エージェント評価用コードは選択したソースと設定をZIPにまとめ、KaggleのPythonスクリプトに埋め込みます。CLIの表示処理、開発用テスト、認証情報、診断資産を含めません。診断用コードは別のZIPにまとめ、モデルやエージェントを含めずに、診断するパッチを渡します。ZIPのSHA-256を実行時に照合します。

事前検証とGPU評価は同じソースZIPを使い、実行種別は起動引数で渡します。モデル宣言の確認と登録はadk-submissionの公式APIへ接続し、旧版の内部モジュールは使用しません。参照検証ではサーバーを起動せずにモデルとLoRAのコンパイルも確認します。

実行順序は、公式依存関係の導入、提出物の検証とZIP生成、正解パッチによる前提検証、推論サーバー起動、公式評価です。各段階と所要時間、推論サーバーに渡す設定とAPIの既定値を記録します。公式側が解決した実際の起動引数は推論ログに残します。公式評価後は保存ファイルを再読込して集計と予定IDを照合し、提出物が変わっていないことを確認して完了とします。公式評価が記録した予期しない処理・保存のエラーも失敗として扱います。Notebookの強制停止で終了処理が実行されない場合も、最後に記録した段階を確認できます。

## 提出物の契約

提出ZIPのルートには`agent.yaml`を置きます。公式のディレクトリ検証、モデル確認、コンパイルを行った後にZIP化し、展開した内容も同じ処理で検証します。生成前後のファイル一覧とハッシュの一致を確認します。

配布LoRAは公式入力から取得し、Gitには含めません。Git上のYAML・プロンプトを重ねて評価対象を準備するため、アダプターを含む完全な提出物はKaggle上で作成します。ローカルだけで公式検証が完了したとは扱いません。

## 結果の契約

エージェント評価には公式の`summary.json`、`task_results.jsonl`、パッチ、検証ログ、トレースをそのまま使います。独自の採点や公式結果の書き換えは行いません。追加する`manifest.json`には、実行種別、実行ID、状態、段階、予定課題、ソースのハッシュ、適用設定、依存関係、環境、時間を保存します。パッチ診断は別の`report.json`へ記録し、解決率を算出しません。

参照検証は`kind=verification`、エージェント評価は`kind=evaluation`として区別します。参照検証では`controls.json`を読み、エージェントの解決率は算出しません。評価開始前の失敗では、公式評価ファイルが未生成であることを許容します。完了済み評価の欠損や、存在するファイルの破損は許容しません。

公式集計は完了した課題が対象です。CLIは予定課題との一致を確認し、重複、欠損、不正な値、集計との不一致がある結果を比較可能な実験として扱いません。解決率は、すべての予定課題が終了し、ファイル間に矛盾がない場合だけ表示します。

比較では対象課題、評価上限、パッチ検証時間、モデル、実行イメージ、推論設定とAPIの既定値、依存関係、データの識別情報を確認します。提出ファイルのハッシュも照合し、プロンプト・エージェント設定・LoRAの変更をファイル名で表示します。提出ファイルの記録がない場合は、同じ条件と判定しません。ソース全体のハッシュは実行の追跡に使用します。

## 配置と生成物

開発環境は`/Users/takafumi/Developer/personal/gemma-4-developer-agent`に置きます。生成物はプロジェクト直下の`artifacts/`へ集約し、ソース・設定・文書と分けます。MakefileとCIは同じ保存先の設定を使います。

Kaggleでは`/kaggle/working/artifacts/results/実行ID/`に結果を保存し、この実行フォルダーを公式ライブラリの作業ディレクトリにします。ソース展開と一時ファイルは`artifacts/tmp/`、KaggleのPythonバイトコード生成は親・子プロセスとも無効にし、出力一覧へ不要なキャッシュを含めません。ローカルのキャッシュは`artifacts/cache/`に置きます。


## 提出候補の固定

`preflight`はローカルの品質・構造・診断を確認し、現在のエージェントと固定したLoRAから候補ZIPを生成します。ローカル検証と公式コンパイルの範囲は別々に記録します。入力・コード・依存関係・診断成果物のハッシュを照合してから、Notebookへ同じZIPを渡します。

`diagnostic_bundle`は診断用Notebookの生成、`diagnostic_kaggle`はKaggle CPUでの実行を担当します。`candidates`は推論環境に依存しないZIP展開と参照検証を担当します。依存方向と数値規則はpyproject.toml、判断基準はコーディング規約で管理します。

モデル停止は結果保存から独立させます。停止・保存・成果物の整合確認がすべて完了した場合だけ、正式提出に使用するZIPを公開します。実行コードを変更した場合は影響する段階を再検証し、結果を文書へ追記しただけの場合はGPUを再実行しません。

# 実験管理

Gitを実験定義と判断の正本にします。モデルの実行データはローカルに保管し、Gitには問題ID、ハッシュ、条件、集計値、短い判断だけを残します。MLflowはGitから再構築できる検索用の複製です。

| 対象 | 責務 |
|---|---|
| `configs/tasks/easy.yaml` | 調整・確認の固定区分と、実験ごとの使用ID・順序 |
| `configs/evaluation/easy-*.yaml` | 比較・最適化の仮説、対象、固定条件、実行予算 |
| `agent/*-v1.yaml`、`agent/prompts/*-v1.md` | 版を付けたエージェント構造と指示 |
| `docs/records/experiments/*.json` | ハッシュと集計値を持つ公開可能な実験記録 |
| `docs/analysis/improvement-strategy.md` | 失敗の原因、改善仮説、採否の判断基準 |
| `artifacts/` | 競技データ、CPU証拠、候補ZIP、個別実行、MLflowのSQLite |

登録したIDの定義を変更する場合は新しいIDを作ります。MLflowへの同期は同じID・同じ内容ならスキップし、内容が異なれば失敗します。MLflow内部の数値IDは記録の識別に使いません。SQLiteを削除してもGitの公開記録から作り直せます。追跡用サーバー、UI、autolog、トレース収集、LLM判定器は使いません。

手書きの解釈はGit上でレビューします。許可するJSONのキーと型を検証し、競技本文、パッチ、ZIP、ログを受け取る汎用フィールドを作りません。プロンプトの登録は自作の未展開指示だけに限定し、課題文の埋込み後の内容は登録しません。同期プロセスはネットワーク接続を拒否します。

MLflow 3.17.2のskinny配布とSQLAlchemy・Alembic・sqlparseをハッシュ固定した専用CPU環境で利用します。開発・公式SDK・Notebook・提出物には依存を追加しません。

## 候補を固定する流れ

1. 実験IDに対応する課題の順序を取得する。実行時に再抽選しない。
2. 準備済みCPU環境と読み込み元を照合し、品質検査と未修正・参照修正の対照検証を行う。
3. 各候補のルートYAMLから参照される指示、子エージェント、サンプリング設定だけをコピーする。ルートを提出用の `agent.yaml` として保存し、同一の検証済みLoRAを追加する。
4. コード、テスト、検査スクリプト、ビルド定義、選択した入力のハッシュが途中で変わっていないことを確認する。
5. 同じソースバンドルを公式SDKのCPU環境でコンパイルする。課題専用CPU環境の対照検証をハッシュ・JUnit・読み込み元まで再照合して結合する。SDK環境へ課題の依存を追加しない。
6. 後のGPU用コード生成では、同一バンドルのCPU記録と観測したquotaを要求する。

無関係な指示や未選択の設定を候補の入力に含めません。過去の登録済み候補と提出状態は再生成しません。

## 共有セッション

評価用バンドルにだけ比較処理を同梱します。モデル、LoRA、サンプリング、評価条件が一致しなければ同じサーバーで比較しません。各課題と候補の組に新しい評価設定・モデル登録・評価器を作り、公式ハーネスが新しい会話と作業領域を作ります。

予定順序と実際に開始した順序を配列で保存します。各セルの実行IDにはセッションIDを含めます。各セルの公式結果は独立した記録にし、SDKの課題番号を書き換えません。セッション全体の終了状態と個別結果も分けます。モデル停止は結果保存とは独立して行い、外側の期限監視がプロセス群を終了させます。送信処理はこの経路にありません。

MLflowの構成は[skinny配布のSQL依存](https://pypi.org/project/mlflow-skinny/)、[SQLiteのbackend store](https://mlflow.org/docs/latest/self-hosting/architecture/backend-store/)、[Prompt Registry](https://mlflow.org/docs/latest/genai/prompt-registry/)を参照しています。確認日：2026年10月21日。

## 比較条件と公開記録

新しい比較定義は、基準候補、比較候補、仮説、変更を許可するファイル、ルートYAMLの変更可能な項目を宣言します。候補を展開した後に実際の差を計算し、宣言外の差、モデル・LoRA・生成・採点条件の差を拒否します。逐次構成は補助担当とLoRAの割当も変わるため、担当構成全体の比較です。

準備、セッション、個別評価、集計の間で、実験ID、定義ハッシュ、ソース、候補、課題と順序を照合します。新しい定義には後継IDを使い、以前の定義や記録は変更しません。

公開記録は、課題別の公式成否、時間、終了理由、実装差分の有無、ツール引数エラー数、実測quotaを持ちます。未実行には実行IDや時間を付けず、未完了には成否を付けません。差分やトレースがなければ未確認です。原因の確認度、採否、親候補、解釈は人が記入します。自動抽出が根本原因や採用を決めることはありません。

公開記録は新規作成だけを許可します。数値と型の検査は競技データやMLflowなしで行えます。過去の記録の読み込みも維持し、書式を変えるために過去の結果を書き換えません。

## Easy課題の巡回

調整36問と確認12問を分離します。予定した課題と、実際に開始・完了した課題を分け、次の課題は未使用を優先します。成績は選択に使いません。リポジトリを順番に巡回し、同じリポジトリではseedと問題IDのSHA-256順を使います。他の実験が予約した課題と確認群を除外します。

件数は設定値です。起動、生成、採点、後始末の上限と、過去2実行からの見積もりを表示します。CPU準備の未計測費用を0秒にしません。提案は実行定義を書き換えず、実行中に課題を交換しません。

## 検証Skillと指示の最適化

Skill比較は既存workflowへ検証手順とPythonスクリプトだけを加えます。宣言したSkill資産も候補の入力とハッシュへ含めます。外部参照、リンク、欠落を拒否します。スクリプトは作業領域を明示し、一つの期限内で実装差分、指定テスト、JUnitを確認します。テスト0件、実装差分なし、タイムアウトを成功にしません。テスト・実装・依存・提出状態は変更しません。

GEPA探索は二候補の比較とは別の定義と入口を持ちます。最初の対象はworkflowの主指示だけです。種候補をコピーし、埋込み変数と他のファイルを固定したまま、新しい指示をZIP・ハッシュ・SDKコンパイルで確定します。

探索3問と選択3問はいずれも調整群です。評価8件、指示生成1回、反省1問、seed 0で始め、候補のマージは使いません。反省には行動上の観測だけを渡し、課題本文や参照修正を渡しません。同じGemmaサーバーで指示を生成し、各呼出し前に回数、期限、入力・出力長を検査します。公式判定が確認できない環境エラーや未完了を0点に変換しません。

モデル起動・停止と公式評価セルは比較経路と共通です。モデルとLoRA以外の会話、作業領域、評価器は共有しません。GEPAはハッシュ固定した専用CPU環境と最適化バンドルへ限定し、MLflow環境と提出ZIPへ追加しません。

最適化のGPU時間・quotaは明示設定が必要です。起動、評価上限、指示生成、CPU準備、後始末から必要時間を計算します。既存比較の90分を既定値にせず、残枠が不明なら生成を止めます。探索結果はローカル候補であり、採用・登録・提出は行いません。

全体の品質検査を含めて完了できるよう、現行の事前検証は`preflight-v2.yaml`でCPU検査の期限を1200秒にします。旧`preflight.yaml`と旧実験定義は当時の600秒を保持します。GPUの比較時間とquotaは変更しません。

## 実行と終了の識別

ソースハッシュはコード、ジョブIDはNotebookの実行を識別します。外側の監視で発行したジョブIDを子プロセス、セッション、個別結果、最適化、診断、ログへ引き継ぎます。監視による中断は、同じジョブIDの実行中記録だけへ反映し、同じコードの過去実行や完了済み結果は変更しません。

新しい対比較記録は、実際の課題・スナップショット・読み込み補正・SDKと、定義の固定条件を照合します。候補間の一致だけでは成立としません。未完了の開始済み課題は使用済みとして残し、未使用群へ戻しません。公式の`filepath`と旧記録の`file_path`・`path`を認識して編集の試行を抽出します。

登録用の元ZIPは展開した候補と別に保存します。対比較の検証は`candidates.experiment_evidence`で行い、提出状態から分離します。種別付きの証拠はCPU・GPUセッションと候補別の個別評価ハッシュを保持し、保存版Notebookの同一ZIPへ接続します。既存の単独評価の記録も読み込みます。

生成時間・ツール予算・ターン数・コンテキスト長の上限は未解決として比較します。公式結果のerror欄を一括で基盤エラーにせず、確認できる終了理由を使います。採点のタイムアウト、一般の実行障害、終了理由が未確認の未完了は、登録可能な完了結果にしません。

## 全体予算と共通対照

新しい実験はGPUジョブ内の準備期限を`session.preparation_timeout_seconds`へ明示します。未設定の過去定義は準備時間不明として読み取り、GPU用生成を許可しません。準備、モデル起動、全課題・候補の生成と採点、後始末の上限を共通計算し、quotaと別に確認します。ローカルCPU検証はこのGPU実行可否と分けます。

準備期限はNotebookの開始を起点にし、バンドル展開と子プロセスの起動も含めます。記録では起動前の準備、依存導入、入力確認、対照検証、モデル起動を分けます。`cpu_seconds`は準備工程を含む合計で、内訳へ重複加算しません。

対照は同一セッションで一度だけ実行し、`controls/shared`へ保存します。`control_evidence`は条件ハッシュ、保存先、ファイルハッシュを持ち、個別評価も同じ参照を保存します。候補ごとのSDKコンパイルと生成パッチ採点は個別です。過去の候補別対照記録は当時の証拠として照合します。

終了手順とSkill利用の改善は、それぞれ`easy-completion-v1`と`easy-skill-use-v1`で主指示だけを比較します。課題はSkill v3の固定6問と順序を引き継ぎます。これらは未評価候補であり、CPU契約の通過を精度向上と扱いません。

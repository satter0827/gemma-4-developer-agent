# 構造とデータの流れ

## コードの責務

| パッケージ | 入出力と責務 |
|---|---|
| common | 設定検証、ハッシュ、保存、プロセス、JUnit、実行ソース一覧 |
| tasks | 課題定義と分類から参照台帳を作る |
| diagnostics | 準備済み課題環境で保存パッチと対照を再現する |
| evaluation | 解決済み実行設定、公式SDK接続、結果照合・比較・GPU予算 |
| candidates | 提出ZIPの生成・検証、現在の事前検証、保存済みCPU/GPU証拠の照合 |
| notebooks | 共通バンドル、単独起動処理、依存導入、Notebook監視 |
| workflows | 既存サービスの接続、工程境界での再開、成果物の受け渡し |
| submission | 登録済み候補に対する提出判断、状態、Git保存、Kaggle API |

ルートCLIは引数解析と振り分け、各機能のCLIはコマンド定義と表示を担当します。パッケージ初期化では処理も再エクスポートも行いません。依存分類と許可方向は`pyproject.toml`、検査は`check_architecture.py`が管理します。関数内や型検査専用のimportも循環の検査対象です。

公式推論SDKは接続モジュールと隔離ワーカーに閉じ込めます。ローカル経路は推論ライブラリへ静的依存せず、importだけで通信・変更・プロセス起動を行いません。Notebookの起動コードは単独で動き、配布するスクリプト名は`run.py`です。

## 設定の責務

| 区分 | 入力 |
|---|---|
| tasks | 全課題の定義、課題文の手動分類、比較候補順、台帳設定 |
| evaluation | プロファイル、推論・生成・採点、事前検証、GPU予算、履歴集計 |
| diagnostics | 診断ケース、期待結果、実行条件 |
| environments | Kaggle資源・マウント先、公式SDK固定情報、CPU依存 |
| submission | 提出方針、保存版取得先と検証証拠を持つ候補記録 |

手書き設定はYAML、SDK固定情報・候補記録はJSON、Python依存は`.in`と`.lock`です。`agent/`は正式提出物として独立し、エージェントの定義形式を維持します。

実行設定はKaggle環境、推論条件、SDK固定情報、課題IDの参照を解決して`RuntimeSettings`へ統合します。参照はプロジェクト内に限定し、重複キーを拒否します。バンドル内では解決済みの単一JSONにします。実行場所による設定階層を増やさず、環境だけを`environments`へ分離します。

## 候補と実行の流れ

事前検証 → 固定ZIP → CPU参照検証 → 同一ソース・同一ZIPのGPU評価 → 保存済み証拠の照合 → 明示登録 → 提出判断の順です。Notebook生成は遠隔実行を開始しません。通常の検証から提出APIは呼びません。

ZIP生成・ハッシュ・起動コード組み立て・Notebookメタデータは共通です。同梱ソースは用途ごとの許可リストを持ち、評価用に診断パッチや診断実行モジュールを含めません。内部importと親パッケージの存在も照合します。起動コードはソースハッシュの対象です。

台帳は固定された全課題の特徴を扱います。履歴集計を明示した場合だけ過去の結果と費用を結合し、分析本文を上書きしません。

## 実験の管理

評価パッケージは実験定義、CPU準備、共有モデルセッション、対応する課題の集計を分離します。課題群の区分と使用履歴はtasks、候補の参照解決とZIP固定はcandidates、実行用バンドルはnotebooksが担当します。MLflowへの同期は専用CPU環境のプロセスだけで行い、評価・提出用バンドルに同梱しません。条件とデータの流れは[実験管理](experiments.md)を参照してください。

## Notebookの転送

起動コードはKaggleのソースサイズ制限より小さく生成します。小さいバンドルは標準ライブラリのLZMAとBase64で埋め込み、展開後に元のZIPのSHA-256を確認します。候補ZIPの内容やバイト列は変更しません。

大きいバンドルは、明示したPrivate Datasetから同じZIPを取得します。Private DatasetはURLの`owner/name`で接続し、ファイルは`/kaggle/input/name/`から取得します。公式Wheelhouseの階層からPrivate Datasetの配置を推定しません。読み込み元をKaggleの入力配下へ限定し、保存先の更新やファイルの変更があればハッシュ照合で停止します。Datasetへの登録、Notebookの遠隔起動は生成と分離した操作です。サイズ上限を超える埋込みは保存前に拒否し、バンドル自体を生成物へ保存します。

課題の共通WheelとSDK専用Wheelは課題定義で区別します。ローカルCPU診断は共通Wheelだけを導入し、Kaggle SDKのサンドボックスには両方を同梱してハッシュ照合します。SDK専用Wheelの変更は実験定義とバンドルを失効させますが、Python・ローカル依存・スナップショットが同一ならローカル環境の再作成は要求しません。

課題群の識別には、選択した実験の用途、データ、SDK、区分を使います。他の実験の予約追加だけで既に固定した最適化を失効させません。選択した課題と順序は定義内で別途照合します。

開発ワークフローは最上位の実行層として既存のローカル処理と候補照合を呼びます。他の機能からワークフローへ依存しません。開発AI用Skillは`.agents/skills/`に置き、提出する`agent/skills/`と分離します。

専用ワーカーは、その中から起動されたSDK・モデルの独立プロセス群を実行ごとに記録します。終了処理と外側の監視は同じ所有記録を使い、PIDの再利用を確認してから停止します。CPU検証も同じ所有境界を使います。評価ごとに新たなワーカーは作りません。

LLMの生成設定は候補のルートから参照を解決し、未参照の固定名ファイルから推測しません。比較で許可する生成条件は`change.generation_fields`へ宣言し、実行時の条件と保存結果を同じ契約で照合します。Skill検証も候補が宣言する資産を読み込みます。

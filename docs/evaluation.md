# 評価と提出の手順

## 基準となる実行

最初は公式スターターの構成と2課題を再現します。配布済みLoRAと補助エージェントを使い、新規学習は行いません。既定の提出YAMLは、コマンド60秒、セッション1分、ツール10回、ターン50回の短時間検証用設定です。1分は競技の必須制限ではありません。公式の生成予算は全課題で12時間で、環境準備を含み、パッチ検証時間は除きます。[公式評価条件](https://www.kaggle.com/competitions/gemma-4-developer-agent/overview)

課題、GPU、モデル、コンテキスト圧縮などの設定はKaggle設定で変更します。比較する実験では、変更した条件を確認してから結果を解釈します。時間制限の比較では、31Bモデル、配布LoRA、プロンプト、思考量、呼び出し回数などを固定し、1分と`configs/evaluation/5min.yaml`の5分を各1回評価します。両設定を同じコードから生成し、ソースZIPの差分が`agent/eval_config.yaml`だけであることを確認します。

両設定のCPU参照検証を通過後、それぞれ同じソースZIPでGPU評価を順番に実行します。この時間制限比較ではGPU評価を計2回とし、自動再試行は行いません。依存関係のファイルハッシュや実行条件が一致しなければ、比較不成立として停止します。解決数だけでなく、編集開始、パッチ生成、提出、公式検証への到達と終了理由を確認します。2課題・各1回の結果を全課題の性能へ一般化しません。

## 探索手順と呼び出し上限の改善

時間制限比較の後、追加の改善とGPU評価が承認されました。次の候補は5分・30回の`configs/evaluation/5min-30tools.yaml`です。31Bモデル、配布LoRA、思考量、コマンド上限、パッチ検証上限は維持します。新しい指示は、隠し設定を含む探索範囲の絞り込み、小さな編集、既存の対象テストと失敗時に非ゼロで終了する確認、残り予算に応じた提出を扱います。

公式の残り呼び出し回数警告は上限20回以上で有効になり、残り10回以下で付与されます。30回設定では、この警告を受けて検証と提出へ移る余地を確保します。`get_status`と`submit_patch`は呼び出し回数に加算されません。[公式配布基盤](https://www.kaggle.com/datasets/metric/gemma-4-developer-agent-wheelhouse)

この候補では指示と呼び出し上限を同時に変えるため、前回との成績差を時間だけ、または指示だけの効果とは扱いません。課題ID、正解パッチ、採点用テスト、既存結果は変更しません。課題固有の修正内容や期待される文言をプロンプトへ埋め込まず、公式判定で解決を確認します。テストの固定文言と課題文の対応は確認事項として残します。

## 主エージェントのLoRA比較

5分・30回の評価でも、同じファイルの再読込とツール引数の生成ミスが残りました。主エージェントの配布LoRAを使わない構成を比較し、探索・編集・提出への影響を調べました。公式判定は両条件とも0/2でした。主LoRA指定は元に戻しています。各条件1回の結果から、LoRAが失敗原因だとは判断しません。

配布された2つのLoRAは同じファイルハッシュで、B行列の全要素がゼロでした。LoRAの重み差分はゼロなので、この比較はアダプターを経由する推論処理の影響を確認するものです。検査記録は`artifacts/kaggle/adapter-20261020-weights-check.json`に保存しています。

この比較では`agent.yaml`の`adapter`指定だけを変更し、31Bモデル、プロンプト、5分・30回の設定、思考量、対象課題、実行環境を固定します。補助エージェントの配布LoRAと提出物内の配布アダプターは維持します。CPU参照検証を通過後、同じソースでGPU評価を1回実行します。課題の成否は公式判定のまま保存します。

## 正解パッチによる検証

評価設定の対象IDから参照検証の課題を選びます。初期対象は`fastapi_15661`と`fastapi_15588`です。すべての対象に正解パッチと検証パッチを必須とし、評価と参照検証で課題集合を一致させます。課題ファイルのハッシュと対象IDを保存します。

公式の検証関数に、空の修正と正解パッチをそれぞれ渡します。修正前が未解決、正解パッチ適用後が解決となることを確認します。終了コードだけでなく、公式のJUnit検証を含む判定を使用します。失敗した課題を別の課題へ自動的に差し替えません。

パッチ検証は`verification_timeout_seconds`の300秒、エージェントのコマンドは提出YAMLの60秒を使用し、公式APIの別々の項目へ渡します。正解パッチは前提検証専用であり、プロンプトには含めません。

GPUなしのPrivate Notebookで事前検証を通過した後、GPU環境でも同じ参照検証をやり直します。事前検証と評価では、ソースのハッシュ、Wheelhouseの版とハッシュ、課題データ、実行イメージを照合します。

## 失敗時の確認

1. Notebookが起動しない場合は、Kaggleの実行状態、GPU枠、モデルの利用条件を確認します。
2. 依存関係の導入に失敗した場合は、公式Wheelhouseの版とログを確認します。未知の版へ自動更新しません。
3. 前提検証に失敗した場合は、修正前と正解パッチ適用後のログを確認し、環境準備と課題の問題を区別します。
4. 推論やツールが停止した場合は、トレースと適用した予算を確認します。空のパッチはその実験の結果として保持します。

Kaggleの開発実行はsubprocess方式です。本番のDocker隔離環境と同じ条件ではないため、ローカルやNotebookでの成功を本番採点の成功とは扱いません。

## 提出前

評価対象のハッシュとZIPの記録を確認し、公式検証が通った提出物を使用します。認証情報、ログ、開発コードを含めません。コンペへの提出はNotebookの実行とは別の操作です。

## 実行状況の確認

公式CLIの`kernels status`、`kernels logs --follow`、`kernels files`、`quota`を使用します。実行中のログは`--follow`で取得します。既定の`kernels logs`は保存済みログを返すため、実行中は空の場合があります。コードの保存版とハッシュを確認したうえで、状態表示、ログ、生成ファイル、GPU枠を照合します。空のログやGPU使用量だけから待機原因を決めません。

公式SDKではQUEUEDが状態の既定値で、JSONでは既定値が省略されます。空の応答を理由にSDKの不具合と判定しません。実行開始後は、ログとmanifestの`phase`で依存関係の準備、提出物の検証、参照パッチの検証、モデル起動、評価のどこまで進んだかを確認します。

推論サーバーのログは実行フォルダーの`vllm.log`に保持します。モデル起動の失敗や終了処理で元の一時ログが削除されても、生成済みのログを確認できます。

結果は新しい取得先を`artifacts/results/`配下に指定してダウンロードします。`kernels output`はページを順次取得し、`--file-pattern`に一致するファイルだけを保存します。展開した提出物やキャッシュを重複して取得しないよう、READMEの取得パターンを使用します。CLIはこの配下のmanifestを検索し、実行IDで結果を選びます。同じ実行IDが複数ある場合は選択せず、重複を報告します。

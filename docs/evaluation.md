# 評価の進め方

操作コマンドはREADMEにまとめています。この文書では実行順序と停止条件を示します。

## ローカル

1. 開発環境、課題環境、SDK確認用CPU環境を別々に準備する。
2. 既存2課題の8条件を診断し、参照パッチの成立と原因の再現を確認する。
3. 事前に固定した候補順で、3リポジトリから2課題ずつ選定する。
4. 合成入力で公式コンパイル、モデル・LoRA登録、生成リクエスト、思考履歴を確認する。
5. 品質チェック後、明示したプロファイルで候補ZIPを固定する。

通常の診断・選定・SDK確認・事前検証はネットワークやGPUを使いません。環境や入力が変わった場合は準備へ戻ります。選定前の環境修正では旧レポートを保持し、新しい検証記録を作ります。モデル評価後は課題を選び直しません。

## Private CPU

公式のコンパイルと、選定した全課題の未修正・参照パッチを確認します。参照パッチの失敗、テストの収集失敗、テスト0件、読み込み元の不一致、保存失敗はGPUへ進めません。通常の未修正の不具合失敗と環境の失敗を分けます。

既存の診断8条件は、診断専用Notebookで確認します。診断用の正解・原因確認用パッチを、エージェント評価用バンドルへ混ぜません。課題選定のための参照パッチもエージェントの入力へ渡しません。

CPU実行のmanifestと制御ケースを取得し、候補ZIP、実行コード、課題順、スナップショット、公式Wheel、ソースの読み込み元を照合します。GPU用コードは同じ証拠から生成します。

## Private GPU

モデルは31B、配布LoRAと補助エージェントを共通にします。現行指示と改善指示を、同じ6課題・同じ順序・5分・30ツール・50ターンで比較します。コマンドは60秒、採点は300秒です。思考量4096、最大出力16384、temperature 0.2、top-p 0.95、seed 0を固定します。

各Notebookは準備と保存・終了も含め45分までです。最大4 quota時間分のうち1時間分を予備として残し、各実行の直前・完了後に公式APIの消費量と回復日時を記録します。L4の過去の実測を使う次回消費の上限見積もりと、実際の消費量を区別します。見積もりが成立しない場合、枠が不明な場合、上限を超える場合は開始しません。

同時実行と自動再試行は行いません。追加測定は全6課題で最大1回とし、予算内に収まる場合だけ行います。比較不能な入力差や環境差があれば、成績の増減を指示の効果とは判断しません。

## 結果と限界

公式の成否は課題単位です。分析では個別テスト、編集、検証行動、時間切れなどの証拠を分け、コマンドの実行だけを検証成功にしません。欠けたトレース、打ち切られた結果、保存不良は明示します。

公開課題の説明に修正内容の手掛かりが含まれる場合もあります。6課題の単回比較は開発判断に使い、非公開課題への一般化や正式スコアの予測には使いません。正式スコア0.01と開発用0/2の関係は採点差の文書を参照してください。

KaggleへのNotebook実行は正式提出ではありません。今回の経路では正式提出用ZIPの自動出力・送信を行いません。過去の時間・LoRA比較は検証状況に残し、現在の比較条件と混同しません。

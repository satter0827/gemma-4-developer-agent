# 改善判断の分類

改善の判断は、観測、原因の確度、対策、採否を分けます。課題の未解決だけから原因を決めず、同じ条件の比較と反証できる検証を対応させます。

| 原因区分 | 観測する症状 | 確認する条件 |
|---|---|---|
| expectation | 指示された入力・公開API・戻り値・例外の取り違え | 課題文の入口から、期待値をassertする再現があるか |
| exploration | 調査を続けても実装へ進まない | 最初の実装変更、調査の範囲、残時間 |
| tool | 編集・実行ツールの引数が受理されない | 応答の引数エラー。生成側か変換側か不明なら断定しない |
| repair | 修正を加えたが期待する挙動が成立しない | 実際の実装差分と公式判定、境界条件 |
| verification | 成功したと判断した検証が課題を捉えていない | 終了コード、テスト件数、公開API、差分、独立した再確認 |
| budget | 生成・ツール・コンテキスト・採点の上限で停止する | 上限の種類、実際の終了理由、開始・完了した課題 |
| environment | 参照修正やテスト収集が環境差で成立しない | 参照と未修正の対照、依存、読み込み元、実行場所 |

確度は`confirmed`（その原因を直接確認）、`hypothesis`（観測に合うが未確定）、`unknown`（判断できる証拠がない）の3区分です。同じ観測から複数の仮説が立つ場合は、確度と限界を付けて併記します。ツールを呼んだこと、実装が変わったこと、テストが通ったこと、課題が解決したことは別々に記載します。

採否は`unevaluated`（モデル評価前）、`inconclusive`（判断保留）、`provisional`（限定条件で有望）、`adopt`（採用）、`reject`（不採用）で表します。CPU契約や合成応答の成功を精度改善の採用理由にしません。自動最適化の最良候補も、明示的な採用前は通常の候補へ登録しません。

完了した個別評価にのみ公式の成否を記録します。未完了の成否、取得できなかった差分、未計測のquotaはnullです。未実行には実行IDや実測時間を付けません。異なる課題群の率を単純に合算せず、同じ課題内の改善・悪化・不変を比較します。

実験IDは仮説と固定条件、候補IDは内容、記録IDは一度の観測と判断を識別します。条件や指示を変える場合は新しいIDを付け、親候補と変更範囲を明記します。予定順序と実際の開始順序を残し、結果を見てから課題を入れ替えません。
